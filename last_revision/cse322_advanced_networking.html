TCP Congestion Control Algorithms (CCA)

🇧🇩 বাংলায় ব্যাখ্যা TCP Congestion Control মানে হলো — নেটওয়ার্কে যখন অনেক বেশি data যায়, তখন congestion (ভিড়) হয়ে packet drop হয়। এই সমস্যা সামলাতে Linux-এ বিভিন্ন Algorithm আছে যেগুলোকে CCA বলে। সহজ কথায়: নেটওয়ার্কে "ট্র্যাফিক জ্যাম" এড়াতে TCP কতটুকু data পাঠাবে সেটা control করাই CCA-র কাজ। সবচেয়ে popular CCA হলো Cubic (Ubuntu-র default), Reno, এবং BBR (Google-এর তৈরি, fastest)।

Linux Commands — Step by Step

Terminal — TCP CCA Commands 
# Step 1: বর্তমান CCA কোনটা চলছে দেখো
$ sysctl net.ipv4.tcp_congestion_control
net.ipv4.tcp_congestion_control = cubic

# Step 2: Available (installed) CCA-গুলো দেখো
$ sysctl net.ipv4.tcp_available_congestion_control
net.ipv4.tcp_available_congestion_control = reno cubic

# Step 3: Kernel-এ installed কিন্তু load হয়নি এমন সব CCA দেখো
$ ls -al /lib/modules/`uname -r`/kernel/net/ipv4/tcp*
... tcp_bbr.ko  tcp_cubic.ko  tcp_reno.ko  tcp_vegas.ko  tcp_westwood.ko ...

# Step 4: নতুন CCA module load করো (bbr example)
$ sudo /sbin/modprobe tcp_bbr

# Step 5: Verify করো — এখন bbr available হয়েছে
$ sysctl net.ipv4.tcp_available_congestion_control
net.ipv4.tcp_available_congestion_control = reno cubic bbr

# Step 6: Temporarily CCA পরিবর্তন করো bbr-এ (-w = write)
$ sudo /sbin/sysctl -w net.ipv4.tcp_congestion_control=bbr
net.ipv4.tcp_congestion_control = bbr
ℹ️
Key Point: sysctl -w দিয়ে যে change করা হয় তা temporary — reboot করলে আগের setting ফিরে আসবে। Permanent করতে /etc/sysctl.conf edit করতে হবে।

Questions & Answers
Q1. TCP Congestion Control কি? এটা কেন দরকার?
Easy
Answer: TCP Congestion Control হলো এমন একটা mechanism যা নেটওয়ার্কে data পাঠানোর হার নিয়ন্ত্রণ করে যাতে network overload না হয়।

কেন দরকার? যদি সব sender একসাথে অনেক data পাঠায়, তাহলে router-এর buffer full হয়ে packet drop হয়। CCA এটা prevent করে window size (কতটুকু data একসাথে পাঠানো যাবে) control করে।
Q2. Linux-এ currently কোন CCA চলছে সেটা কিভাবে দেখবে? Command লেখো।
Easy
Answer:
sysctl net.ipv4.tcp_congestion_control

এই command টি kernel parameter check করে। Output হবে:
net.ipv4.tcp_congestion_control = cubic

এখানে sysctl = system control (kernel parameters manage করার tool), net.ipv4 = IPv4 network subsystem।
Q3. modprobe এবং sysctl -w এর মধ্যে পার্থক্য কি?
Medium
Answer:
modprobe tcp_bbr — একটা kernel module (যেমন tcp_bbr.ko) memory-তে load করে। Module load না হলে সেই CCA use করা যাবে না।

sysctl -w net.ipv4.tcp_congestion_control=bbr — Already loaded module-কে active/use করার জন্য। এটা temporary (reboot করলে পূর্বের setting ফিরে আসে)।

সহজ ভাষায়: modprobe দিয়ে "install" করো, sysctl দিয়ে "select" করো।
Q4. ls -al /lib/modules/`uname -r`/kernel/net/ipv4/tcp* — এই command-এ backtick (`) কেন ব্যবহার করা হয়েছে? এটা কি করে?
Hard
Answer: Backtick (`) দিয়ে command substitution করা হয়। `uname -r` first execute হয় এবং current kernel version (যেমন 5.15.0-88-generic) return করে। তারপর সেই value path-এ বসে।

ফলে পুরো command হয়: ls -al /lib/modules/5.15.0-88-generic/kernel/net/ipv4/tcp*

এটা dynamic — যেকোনো kernel version-এ কাজ করবে hardcode না করেও।
Q5. BBR vs Cubic — কোথায় কোনটা বেশি উপযুক্ত এবং কেন? (Advanced)
Advanced
Answer:
Cubic: Loss-based — packet drop হলে তবেই window কমায়। High bandwidth-delay product (BDP) network-এ efficient। Local/datacenter network-এ ভালো।

BBR (Bottleneck Bandwidth and RTT): Model-based — continuously bandwidth এবং RTT measure করে। Packet loss ছাড়াও congestion detect করতে পারে। Long-fat network (high bandwidth, high latency), satellite links, cross-continent connections-এ Cubic-এর চেয়ে 2-25x faster হতে পারে।

মূল পার্থক্য: Cubic "loss signal" দেখে react করে। BBR "bandwidth model" maintain করে proactively।
02

Traceroute — An Advanced Command

🇧🇩 বাংলায় ব্যাখ্যা Traceroute হলো এমন একটা command যা দিয়ে জানা যায় — আমার computer থেকে কোনো destination (যেমন google.com) পর্যন্ত packet যেতে মাঝে কত কত router (hop) পার করে যায়। ধরো তুমি ঢাকা থেকে কোথাও চিঠি পাঠাচ্ছো — traceroute দিয়ে জানতে পারবে চিঠি কোন কোন ডাকঘর হয়ে গেছে এবং প্রতিটায় কতক্ষণ সময় লেগেছে।

Windows-এ: tracert | Linux/Unix-এ: traceroute

Traceroute কিভাবে কাজ করে? (TTL Trick)

  1. Source থেকে TTL=1 দিয়ে probe packet পাঠায় destination-এর দিকে।

  2. প্রতিটা router packet receive করে TTL থেকে 1 কমিয়ে দেয়।

  3. TTL = 0 হলে router ওই packet drop করে দেয় এবং Source-কে ICMP "TTL Exceeded" message পাঠায়।

  4. Source সেই ICMP message দেখে বুঝতে পারে hop-টা কোন router। তার IP address ও response time দেখায়।

  5. আবার TTL=2 দিয়ে পাঠায় — এভাবে পরবর্তী router পাওয়া যায়।

  6. Destination-এ পৌঁছালে সে ICMP "Destination Unreachable" পাঠায় (কারণ সে ওই port-এ কোনো app expect করছিল না)।

tracert google.com (Windows output) 
C:\Users\User>tracert google.com

Tracing route to google.com [142.251.10.102]
over a maximum of 30 hops:

  1   3 ms   2 ms   1 ms  192.168.0.1     ← তোমার Router (Default Gateway)
  2  10 ms   4 ms   2 ms  10.0.2.1        ← ISP এর First Router
  3   5 ms  13 ms   2 ms  10.100.0.1
  4  44 ms  30 ms   3 ms  43.224.112.136
  5   4 ms   5 ms   6 ms  103.124.224.10
  7   *      *      *    Request timed out.  ← Firewall drop করছে
 24  51 ms  58 ms  53 ms  sd-in-f102.1e100.net [142.251.10.102]  ← Google!

Trace complete.

Traceroute-এর গুরুত্বপূর্ণ তথ্য

  • 3 Time values: প্রতি hop-এ ৩টা time দেখায় (৩টা probe পাঠানো হয়) — এগুলো Round Trip Time (RTT) in milliseconds।
  • "Request timed out" / * * *: মানে ওই router ICMP reply দেয়নি — সাধারণত firewall block করছে।
  • ICMP src address: Traceroute যে IP দেখায় সেটা হলো router-এর ingress interface IP — egress interface দেখা যায় না।
  • Latency: Traceroute শুধু round-trip দেখায় (forward + reverse path)। তাই reverse path-এ delay থাকলে সেটাও latency-তে add হয়।
  • UDP port: Traceroute normally একটা pseudorandom high port-এ UDP packet পাঠায় (যেখানে কোনো app listen করছে না) — তাই destination থেকে "Dest Unreachable" আসে।
⚠️
Exam Trap: Traceroute "hops on forward path" দেখায়, কিন্তু "latency based on forward PLUS reverse path" measure করে। Reverse path-এ যদি asymmetric routing থাকে তাহলে latency misleading হতে পারে।
Questions & Answers
Q1. Traceroute কি? Windows ও Linux-এ command কি?
Easy
Traceroute হলো একটা network diagnostic tool যা source থেকে destination পর্যন্ত packet-এর path trace করে — মাঝের প্রতিটা router (hop) এবং তাদের latency দেখায়।

Windows: tracert google.com
Linux/Unix: traceroute google.com
Q2. Traceroute-এ TTL কিভাবে ব্যবহার হয়? Step by step বলো।
Medium
Step 1: Src থেকে TTL=1 দিয়ে packet পাঠায়।
Step 2: Router 1 packet পায়, TTL decrements (1→0), packet drop করে, src-কে ICMP TTL Exceeded পাঠায়।
Step 3: Src সেই ICMP-এর source IP (Router 1-এর ingress IP) display করে — এটাই hop 1।
Step 4: এবার TTL=2 দিয়ে আবার পাঠায়। Router 2-এ একই ঘটনা।
Step 5: এভাবে TTL বাড়াতে থাকে যতক্ষণ না destination পায়।
Final: Destination থেকে ICMP Dest Unreachable আসে।
Q3. Traceroute output-এ "* * *" মানে কি? এর কারণ কি?
Medium
মানে: ওই hop-এ কোনো response পাওয়া যায়নি — "Request timed out"।

কারণ হতে পারে:
  • Firewall ICMP TTL Exceeded reply block করছে
  • Router configured করা আছে ICMP না পাঠাতে
  • Packet lost হয়েছে
Note: Intermediate hop-এ * দেখালেই মানে নয় destination unreachable — পরের hop-এ response আসতে পারে।
Q4. Traceroute কোন port-এ কোন protocol use করে? Last hop কি return করে এবং কেন?
Hard
Protocol: UDP (Unix-এ default), ICMP (Windows-এ tracert), বা TCP (option দিয়ে).

Port: UDP traceroute একটা pseudorandom high port (যেমন 33434+) use করে — এই port-এ সাধারণত কোনো application listen করে না।

Last hop কি return করে: ICMP Destination Port Unreachable — কারণ destination সেই port-এ packet পেয়েছে কিন্তু কোনো app সেখানে নেই, তাই "port unreachable" error পাঠায়। এটাই traceroute-এর termination signal।
Q5. Traceroute latency কিভাবে calculate করে? Asymmetric routing কিভাবে result-কে affect করে?
Advanced
Calculation:
1. Probe packet পাঠানোর সময় timestamp নেয়
2. ICMP response পাওয়ার সময় timestamp নেয়
3. পার্থক্যই হলো Round-Trip Time (RTT)

Asymmetric Routing Problem: Forward path আর reverse path different হতে পারে (different routers হয়ে)। Traceroute শুধু forward path-এর hops দেখায় কিন্তু RTT = forward delay + reverse delay। তাই:
→ Hop 5-এ high latency দেখালে সেটা hop 5-এর forward delay নাও হতে পারে — reverse path-এর delay-ও থাকতে পারে।
→ Egress interface-এর IP দেখা যায় না — শুধু ingress দেখা যায়।
03

Nmap — Network Mapper (Advanced Tool)

🇧🇩 বাংলায় ব্যাখ্যা Nmap (Network Mapper) হলো একটা অত্যন্ত powerful network scanning tool। এটা দিয়ে জানা যায়: কোন host আছে নেটওয়ার্কে, কোন ports open আছে, কোন services চলছে, OS কি, network topology কেমন। Nmap এতটাই powerful যে অনুমতি ছাড়া অন্যের network-এ use করলে illegal। Zenmap হলো Nmap-এর GUI version।
🚨
Warning: Nmap is "Extremely powerful, Extremely invasive, Extremely obvious, and Extremely illegal if not done correctly." শুধু নিজের network বা explicit permission পাওয়া network-এ use করো।

Nmap-এর 6টি Port States

State মানে কি? কারণ
Open Port খোলা আছে কোনো application TCP/UDP connection accept করছে
Closed Port বন্ধ আছে Host alive কিন্তু কোনো app listen করছে না। পরে try করা যাবে।
Filtered Filtered হচ্ছে Firewall probe packet drop করছে — no response. Nmap বারবার retry করে।
Unfiltered Accessible কিন্তু অনিশ্চিত Port পাওয়া যাচ্ছে কিন্তু open না closed বলা যাচ্ছে না
Open|Filtered Open বা Filtered — অজানা UDP scan-এ হয়, কোনো response না এলে
Closed|Filtered Closed বা Filtered — অজানা IP ID idle scan-এ হয়

Nmap Intense Scan Command

nmap — Command Line 
# Regular Scan (simple)
nmap google.com

# Intense Scan (Zenmap default intense profile)
nmap -T4 -A -v google.com
#   -T4    = Timing template (4 = aggressive, fast)
#   -A     = OS detection + version detection + script scan + traceroute
#   -v     = Verbose output

# Scan specific port range
nmap -p 1-1000 192.168.1.1

# SYN Stealth Scan (most common)
nmap -sS 192.168.1.1

Nmap Zenmap Tabs — কি কি দেখা যায়

Tabকি দেখায়
Nmap Outputপুরো scan-এর detailed text output — ports, services, OS detection
Ports/HostsOpen ports list — Port number, Protocol, State, Service, Version
TopologyGraphical network map — কোন router হয়ে কোথায় গেছে (fisheye view)
Host DetailsOS guess, open/closed/filtered port count, MAC, hostname, uptime
Scansসব scan history
💡 Google.com scan result বোঝা Google scan করলে দেখা যাবে: Open ports: 2 (80/tcp = HTTP, 443/tcp = HTTPS), Filtered: 998 (Google-এর firewall বাকি সব block করছে)। 1000টা port scan হয়েছে।
Questions & Answers
Q1. Nmap কি? এটা দিয়ে কি কি জানা যায়?
Easy
Nmap (Network Mapper) একটা open-source network discovery ও security auditing tool।

Nmap দিয়ে জানা যায়:
  • নেটওয়ার্কে কোন hosts active আছে
  • কোন ports open/closed/filtered
  • কোন services ও কোন version চলছে
  • Target-এর Operating System কি
  • Network topology (traceroute সহ)
Q2. Nmap-এর 6টি port state-এর নাম এবং প্রতিটার মানে লেখো।
Medium
1. Open — Application actively TCP connection বা UDP packet accept করছে
2. Closed — Host reachable কিন্তু কোনো application port-এ listen করছে না
3. Filtered — Firewall probe block করছে, Nmap response পাচ্ছে না
4. Unfiltered — Port accessible কিন্তু open না closed নিশ্চিত করা যাচ্ছে না
5. Open|Filtered — Open বা filtered নির্ধারণ করা যাচ্ছে না
6. Closed|Filtered — Closed বা filtered নির্ধারণ করা যাচ্ছে না
Q3. nmap -T4 -A -v google.com — প্রতিটা flag কি করে?
Medium
-T4 → Timing template 4 (Aggressive) — scan দ্রুত করে। T0=paranoid (slowest), T5=insane (fastest)
-A → All-in-one: OS detection + version detection + script scanning + traceroute একসাথে
-v → Verbose — scan চলার সময় detailed output দেখায়
google.com → Target host (domain name বা IP দেওয়া যায়)
Q4. Google-এর scan-এ 998 ports filtered দেখায় কেন?
Hard
Google-এর infrastructure-এ enterprise-grade firewall আছে। ওই firewall নেটওয়ার্কের edge-এ বসে আছে এবং যেসব port-এ actual service নেই (অর্থাৎ 80 ও 443 ছাড়া) সেসব port-এর probe packet silently drop করে দেয়। "Stealth drop" করলে Nmap-এর কাছে কোনো response আসে না — তাই state হয় "Filtered"।

Open ports (80 HTTP, 443 HTTPS) এ Google-এর GWS (Google Web Server) actively listen করে তাই সেগুলো "Open"।
Q5. Filtered এবং Closed-এর মধ্যে গুরুত্বপূর্ণ পার্থক্য কি? কোনটা attacker-এর জন্য বেশি useful?
Advanced
Closed port: Host RST (Reset) packet পাঠায় — মানে host alive এবং সেখানে কোনো service নেই। Host-এর existence confirm হয়।

Filtered port: Firewall packet drop করে — কোনো response নেই। Host alive কিনা সেটাও uncertain। Nmap retry করে, scan অনেক slow হয়।

Attacker-এর দৃষ্টিকোণ: "Closed" state বেশি useful কারণ এটা confirm করে যে host exists এবং সেই port-এ future service আসতে পারে। "Filtered" মানে firewall আছে — attack কঠিন।
04

Load Balancing

🇧🇩 বাংলায় ব্যাখ্যা Load Balancing মানে হলো — অনেক client একসাথে service request করলে সেই load (কাজ) একটা single server-এ না দিয়ে multiple servers-এ ভাগ করে দেওয়া। যেমন Google-এ লক্ষ লক্ষ মানুষ request করে — একটা server দিয়ে possible না। তাই একটা Load Balancer মাঝে বসে সব request গ্রহণ করে এবং পেছনের বিভিন্ন server-এ distribute করে দেয়।

Analogy: ব্যাংকে অনেক customer এলে একটা token system করে বিভিন্ন counter-এ পাঠানো হয় — এটাই Load Balancing।

Load Balancing Architecture

Clients → Internet → Load Balancer → Multiple Backend Servers

  • Client সরাসরি জানে না কোন server handle করছে
  • Load Balancer একটা single IP/domain দেখায় (Virtual IP)
  • Backend server fail করলে Load Balancer অন্য server-এ redirect করে
  • এটা High Availability এবং Scalability নিশ্চিত করে

Load Balancing Algorithms

Algorithmকিভাবে কাজ করে
Round Robinএকের পর এক server-এ পাঠায় (1→2→3→1→2→3...)
Least Connectionsসবচেয়ে কম active connection যে server-এ সেখানে পাঠায়
IP HashClient IP দিয়ে hash করে same server-এ পাঠায় (session sticky)
Weightedশক্তিশালী server বেশি load নেয়
Questions & Answers
Q1. Load Balancing কি এবং কেন দরকার?
Easy
Load Balancing হলো incoming network traffic বা client requests-কে multiple servers-এর মধ্যে distribute করার process।

কেন দরকার:
  • Single server overload prevent করতে
  • High Availability নিশ্চিত করতে (একটা fail হলে অন্যটা নেয়)
  • Response time কমাতে ও performance বাড়াতে
  • Scalability — traffic বাড়লে নতুন server যোগ করা যায়
Q2. Load Balancer ও Default Gateway-এর মধ্যে পার্থক্য কি?
Hard
Default Gateway: একটি router যা local network থেকে unknown/external network-এ packet পাঠায়। প্রতিটা device একটাই default gateway use করে। Default gateway fail করলে বাইরে যাওয়া বন্ধ।

Load Balancer: Specifically client requests distribute করার জন্য। Multiple backend servers manage করে। Application layer (L7) বা Transport layer (L4)-এ কাজ করতে পারে।

একটা Load Balancer ব্যবহার করে Default Gateway-র single point of failure সমস্যা solve করা হয় (VRRP দিয়ে multiple gateway রাখা যায়)।

VRRP — Virtual Router Redundancy Protocol

🇧🇩 বাংলায় ব্যাখ্যা সমস্যা: প্রতিটা device এর একটাই Default Gateway থাকে। সেই gateway (router) যদি fail করে, তাহলে পুরো নেটওয়ার্ক বাইরের সাথে যোগাযোগ হারিয়ে ফেলে।

সমাধান: VRRP — দুটো (বা বেশি) Physical Router মিলে একটা Virtual Router তৈরি করে। Client একটাই IP (Virtual IP) জানে। একটা router হয় Active (Master) এবং বাকি router হয় Passive (Backup)। Active fail করলে automatically Passive active হয়ে যায় — client কিছুই টের পায় না!

VRRP Architecture

  • Virtual IP (VIP): 10.1.1.100 — Clients এই IP-কে Default Gateway হিসেবে জানে
  • R1 (Active/Master): 10.1.1.1/24 — VIP handle করছে
  • R2 (Passive/Backup): 10.1.1.2/24 — Monitor করছে, ready আছে
  • Failover: R1 fail → R2 automatically VIP নিয়ে Master হয়
  • Router-এর 2 plane: Control Plane (routing decision) + Data Plane (actual packet forwarding)
Questions & Answers
Q1. VRRP কি? কেন use করা হয়?
Easy
VRRP (Virtual Router Redundancy Protocol) একটা network protocol যা multiple physical routers-কে একটা virtual router হিসেবে present করে। এটা default gateway-র redundancy নিশ্চিত করে।

কেন use করা: Default gateway fail হলে network connectivity হারানো prevent করতে। VRRP active router fail হলে backup automatically takeover করে।
Q2. VRRP-এ Control Plane এবং Data Plane কি?
Medium
Control Plane: Router-এর "brain" — routing decisions নেয়। Routing table maintain করা, neighbor discovery, protocol processing (OSPF, BGP, VRRP)।

Data Plane: Actual packet forwarding — Control plane-এর decision অনুযায়ী packet কোন interface দিয়ে forward করতে হবে সেটা execute করে।

Analogy: Control Plane = GPS (রাস্তা ঠিক করে), Data Plane = Driver (সেই রাস্তায় গাড়ি চালায়)।
Q3. Load Balancing এবং VRRP কিভাবে complement করে?
Advanced
VRRP gateway-level redundancy দেয় — multiple routers থেকে একটা Virtual Gateway।
Load Balancing server-level distribution দেয় — multiple backend servers-এ traffic distribute।

একসাথে use করলে: Client → VRRP Virtual Gateway (High Availability) → Load Balancer → Multiple Servers (Scalability)।
Full high availability architecture-এ দুটোই লাগে।

SDN — Software Defined Networking

🇧🇩 বাংলায় ব্যাখ্যা Traditional networking-এ প্রতিটা router নিজেই সব decision নেয় (Control Plane + Data Plane একসাথে থাকে)। তাই অনেক router configure করতে হলে একটা একটা করে login করে setting পরিবর্তন করতে হয় — অনেক সময়সাপেক্ষ।

SDN এটা বদলে দিয়েছে। SDN-এ সব router-এর Control Plane (intelligence) তুলে নিয়ে একটা central SDN Controller-এ দেওয়া হয়। Router শুধু Data Plane করে (packet forward করে) — "Dumb router" বলা হয়। Controller API-র মাধ্যমে সব router-কে একসাথে control করে।

API to Data Plane: OpenFlow (সবচেয়ে popular protocol)

Traditional vs SDN

AspectTraditional NetworkingSDN
Control Planeপ্রতিটা router-এ আলাদাCentral SDN Controller-এ
Data Planeপ্রতিটা router-এপ্রতিটা router-এ (same)

Questions & Answers
Q1. SDN কি? Traditional networking থেকে কিভাবে আলাদা?
Easy
SDN (Software Defined Networking) একটা networking approach যেখানে Control Plane-কে Data Plane থেকে আলাদা করে একটা central controller-এ রাখা হয়।

Traditional: প্রতিটা router নিজেই সব decision নেয় — distributed control।
SDN: Central SDN Controller সব decision নেয়, router শুধু packet forward করে।
Q2. SDN-এ "Northbound API" এবং "Southbound API" কি?
Hard
Northbound API: SDN Controller ↔ Applications। Applications (যেমন network management apps, security apps) Controller-এর সাথে communicate করে এই API দিয়ে। Programmer এখানে code লিখে network control করে।

Southbound API: SDN Controller ↔ Network Devices (routers/switches)। Controller device-কে flow rules inject করে এই API দিয়ে। Most common protocol: OpenFlow।

মনে রাখার উপায়: North (উপরে) = Apps, South (নিচে) = Hardware devices।
Q3. SDN-এ router-কে "Dumb router" বলা হয় কেন?
Medium
Traditional router-এ Control Plane থাকে — সে নিজেই routing decision নিতে পারে (OSPF route calculate করে, routing table maintain করে)। তাই সে "intelligent"।

SDN-এ router-এর Control Plane তুলে নেওয়া হয়েছে — সে শুধু Controller-এর instructions অনুযায়ী packet forward করে। নিজে কোনো intelligence নেই — তাই "Dumb" (বোকা)।

Benefit: Cheap commodity hardware use করা যায়, software-এ সব intelligence।

Network Virtualization — Overlay, Underlay & VXLAN

🇧🇩 বাংলায় ব্যাখ্যা Network Virtualization মানে হলো — physical network-এর উপরে আলাদা আলাদা virtual network তৈরি করা। দুটো end device যদি physically আলাদা জায়গায় থাকে, তারা যেন মনে করে একই local network-এ আছে।

Server Virtualization (আগে এসেছিল): একটা Physical Server-কে ভাগ করে অনেক Virtual Machines (VM) তৈরি। তাদের মধ্যে communicate করার জন্য vSwitch ব্যবহার হয়।

Underlay: Physical network (real routers, switches, cables)
Overlay: Physical network-এর উপরে তৈরি virtual network — actual physical topology দেখা যায় না।

VLAN limitation: VLAN ID 12-bit → maximum 4096টা VLAN। Large datacenter-এর জন্য যথেষ্ট না।
VXLAN solution: 24-bit ID → 16 million+ virtual networks।

VXLAN — Virtual Extensible LAN

  • VXLAN ID: 24-bit (VLAN-এর 12-bit এর বদলে) → ~16 million networks possible
  • Tunnel: Layer 2 frames কে Layer 3 (IP) packet-এর ভেতরে encapsulate করে পাঠায়
  • VTEP: VXLAN Tunnel End Point — tunnel-এর starting ও ending point
  • Leaf switch: Server-এর directly connected switch (bottom layer)
  • Spine switch: Leaf switches-এর interconnect (top layer)
  • L2 VXLAN Gateway: Same layer-এর VMs communicate করে
  • L3 VXLAN Gateway: Different subnet-এর VMs communicate করে
  • IPv6 payload-ও VXLAN tunnel-এর মাধ্যমে পাঠানো যায়
Questions & Answers
Q1. Network Virtualization কি? Overlay ও Underlay এর পার্থক্য বলো।
Easy
Network Virtualization হলো physical network infrastructure-এর উপরে multiple logical/virtual networks তৈরির process।

Underlay: Physical infrastructure — real routers, switches, cables, actual IP network।
Overlay: Underlay-এর উপরে তৈরি virtual network — end devices underlay-এর জটিলতা দেখতে পায় না, মনে হয় সরাসরি connected।
Q2. VLAN 4096টা limit কেন এবং VXLAN কিভাবে এটা solve করে?
Medium
VLAN limit: VLAN ID field হলো 12-bit। 2¹² = 4096। তাই সর্বোচ্চ 4096টা VLAN হতে পারে। বড় cloud datacenter-এ হাজার হাজার tenant (customer) থাকে — 4096 যথেষ্ট না।

VXLAN solution: VXLAN Network Identifier (VNI) হলো 24-bit। 2²⁴ = 16,777,216 (16 million+)। এত বেশি virtual network তৈরি করা যায় — cloud-scale datacenter support করে।
Q3. VTEP কি? VXLAN-এ এর role কি?
Hard
VTEP (VXLAN Tunnel End Point): VXLAN tunnel-এর starting ও ending device। এটা source-এ L2 frame নিয়ে L3 UDP packet-এর ভেতরে encapsulate করে (VXLAN header add করে) পাঠায়। Destination-এ আরেকটা VTEP decapsulate করে original L2 frame বের করে দেয়।

সাধারণত VTEP হয় Leaf switch বা vSwitch (hypervisor-এ)। VTEP দুটো কাজ করে: encapsulation (সময়: send) এবং decapsulation (সময়: receive)।

Data Centers & Disaster Recovery (DC-DR)

🇧🇩 বাংলায় ব্যাখ্যা যেকোনো organization-এর Data Center হলো তার মূল IT infrastructure। কিন্তু disaster (earthquake, flood, fire) হলে? তাই আলাদা একটা Disaster Recovery (DR) site রাখা হয়। DR site হলো একটা backup datacenter যেখানে main datacenter fail হলে operations চালু রাখা যায়।

DR site develop করার সময় earthquake zone একটা গুরুত্বপূর্ণ বিষয়। Main DC ও DR site একই earthquake zone-এ থাকলে দুটোই একসাথে ক্ষতিগ্রস্ত হতে পারে। বাংলাদেশে Zone I, II, III আছে।
❄️ Cold Site
  • Little/no equipment
  • No network connectivity
  • No automatic failover
  • No data synchronization
  • High risk of data loss
  • Cheapest option
🌡️ Warm Site
  • Partially redundant equipment
  • Network connectivity enabled
  • Failover within hours
  • Daily/weekly sync
  • Minimum data loss
  • Cost-effective ✓
🔥 Hot Site
  • Fully redundant equipment
  • Network connectivity enabled
  • Failover within hours/days
  • Near real-time data sync
  • Zero data loss
  • Most expensive

Questions & Answers
Q1. Cold Site, Warm Site, Hot Site-এর পার্থক্য table আকারে লেখো।
Easy
Cold Site: Equipment নেই, connectivity নেই, data sync নেই। Failover: days/weeks। Data loss: High। Cost: Cheapest।

Warm Site: Partial equipment, network enabled, daily/weekly sync। Failover: hours। Data loss: Minimum। Cost: Moderate (Cost-effective)।

Hot Site: Full redundant equipment, network enabled, near real-time sync। Failover: minutes/hours। Data loss: Zero। Cost: Most expensive।
Q2. DR site develop করার সময় earthquake zone কেন consider করা হয়?
Medium
Disaster Recovery-র মূল উদ্দেশ্য হলো — যদি Primary datacenter destroy হয় তাহলেও operations চালু রাখা। কিন্তু যদি Primary DC ও DR site একই seismic/earthquake zone-এ থাকে, তাহলে একটা বড় earthquake উভয়কে ক্ষতিগ্রস্ত করতে পারে।

তাই DR site আলাদা earthquake zone-এ রাখা হয়। বাংলাদেশে Zone I (0.08g), Zone II (0.05g), Zone III (0.04g) — Sylhet Zone I-এ (সবচেয়ে বেশি risk)। DR site সাধারণত different zone-এ রাখা হয়।
Q3. RPO এবং RTO এর মধ্যে পার্থক্য কি? একটি bank-এর জন্য ideal values কত হওয়া উচিত?
Hard
RTO (Recovery Time Objective): Disaster-এর পর থেকে systems restore হওয়া পর্যন্ত সর্বোচ্চ acceptable time। যেমন RTO = 4 hours মানে 4 ঘণ্টার মধ্যে সব service চালু করতে হবে।

RPO (Recovery Point Objective): সর্বোচ্চ কতটুকু data loss acceptable। যেমন RPO = 1 hour মানে disaster-এর আগের 1 ঘণ্টার data হারানো acceptable।

Bank-এর জন্য: RTO = near zero (minutes), RPO = near zero (seconds) — কারণ financial transactions এ data loss বা downtime catastrophic। তাই Hot Site mandatory।
Q4. (Advanced) একটি organization কেন Warm Site পছন্দ করে Hot Site-এর বদলে?
Advanced
Cost vs Risk tradeoff:

Hot Site maintain করতে প্রায় Primary DC-এর সমান খরচ — fully redundant hardware, real-time data replication, 24/7 staffing। বেশিরভাগ organization-এর জন্য এই খরচ justify করা কঠিন।

Warm Site advantages:
  • Cost significantly কম (Hot site-এর 30-50%)
  • Most scenarios-এ hours-level failover acceptable
  • Daily backup দিয়ে acceptable RPO achieve করা যায়
  • Hardware partially ready — setup সময় moderate
Critical financial/healthcare sectors Hot site নেয়, অন্যরা Warm site prefer করে।
